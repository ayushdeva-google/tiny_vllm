From Math to Silicon

Deriving FlashAttention
From Math to Silicon

How a first-principles derivation of Online Softmax took an 8,192-token prompt from a CUDA OOM to a kernel that runs cleanly at 16k, and made decode 1.3x faster than PyTorch's native path.

The Problem

We already know thread blocks, warps, and how to fuse RMSNorm. But the moment LLaMA-3.2-1B sees an 8,192-token context, standard attention crashes a 24 GB L4 with CUDA Out-of-Memory.

The Approach

Don't memorize Tri Dao's paper. Derive it from memory physics: every byte written to HBM is an engineering failure if it could have lived in registers.

Act 1 · Mathematical Anatomy

A Simpler Problem: One Head, Row by Row

Before wrestling with GPU silicon, let's deconstruct the formula: Softmax(Q Kᵀ) · V. Attention operates across multiple heads, but heads are completely independent. Let's isolate a single head first.

1. Inputs & Dimensions

For 1 head with prompt length N = 8,192 and head dimension d = 64:

Q : [N × d] = [8192 × 64]
K : [N × d] = [8192 × 64]
V : [N × d] = [8192 × 64]

LLaMA has 32 query heads, but they share zero data. Solve 1 head, and you've solved all 32.

2. Q Kᵀ produces [N × N]

Multiplying [N × d] × [d × N] yields an [8192 × 8192] matrix.

Row i = Query token <i> querying all keys <j>
Score(i, j) = (Qi · Kjᵀ) / √d (scalar)
Row Si : [1 × N] = [1 × 8192]

Each entry is a scalar denoting how strongly query <i> attends to preceding key <j>.

3. Row Softmax & V Blending

Softmax is taken row by row. Row Si becomes probabilities Pi.

Pi = Softmax(Si) : [1 × N] row vector
Oi = Pi · V : [1 × N] × [N × d]
    = [1 × d] = [1 × 64] output vector

Softmax is a 1D row; V is a 2D matrix. We add the value vectors of keys in exact softmax proportion!

Observation

Output row Oi depends only on query row i and the shared K, V matrices. Every row is independent. Yet PyTorch doesn't compute row by row: it materializes all 8,192 rows for all 32 heads in global VRAM at once.

Question

If the math never needs the whole matrix at once, how much memory is PyTorch actually spending to hold it, and what happens at 8,192 tokens?

Act 1 · The Crime Scene

The Catastrophe: The Memory Wall

Standard attention is mathematically clean, but the way our model computes it allocates several full N × N tensors per layer. On long contexts that kills the GPU.

# Attention as written in our LLaMA model
# Q, K: [Batch, Heads=32, N=8192, d=64], BF16
scores = torch.matmul(Q, K.transpose(-2, -1)) / 8.0
mask   = torch.full((N, N), -inf).triu(1)
scores = scores + mask
probs  = F.softmax(scores, dim=-1, dtype=torch.float32).to(bf16)
return torch.matmul(probs, V)

Every red line allocates a fresh N × N × 32 tensor. The FP32 softmax (done for numerical safety) is the biggest single allocation.

The Physics of the Crash

For N = 8,192 tokens and H = 32 heads:

scores (BF16): 32 × 8192² × 2 B = 4.0 GiB
scores + mask: another 4.0 GiB
softmax (FP32): 32 × 8192² × 4 B = 8.0 GiB
cast to BF16: another 4.0 GiB
Transient total ≈ 20 GiB on a 22 GiB card

Measured: 5.06 GiB peak at 4k, and OOM at 8k on the L4, before model weights or the KV cache are even counted. Even the leanest eager formulation (bool mask, BF16 softmax) needs 8.16 GiB at 8k and dies at 12k.

Observation

The inputs are small: for one head, Q, K, V are 1 MB each and the output row block O is 1 MB. For the whole layer (32 query heads, 8 KV heads) that's ~48 MB in and 32 MB out. The gigabytes are entirely intermediate. If we stream keys through on-chip SRAM and accumulate into registers, the N × N matrix never needs to exist.

Question

Softmax needs the max and sum over the entire row before it can normalize a single probability. How can we compute it chunk by chunk without ever seeing the full row?

Act 1 · Mathematical First Principles

The Trap: Softmax Needs Global State

To avoid writing the N × N matrix to VRAM, we must compute attention in tiles. But standard softmax requires seeing every single token before calculating even one probability.

Pass 1 · Row Max

m = maxj(Sj)

Prevents numerical overflow when evaluating e(Sj - m). Must scan all 8,192 values.

Pass 2 · Denominator

l = Σ e(Sj - m)

Sums all rescaled exponentials to normalize probabilities. Must scan all 8,192 values again.

Pass 3 · Accumulation

O = Σ (e(Sj - m) / l) · Vj

Multiplies normalized probabilities by values and sums into the output vector.

Observation

All three passes depend on the row max m. If we process chunk 1 using its local max, and chunk 2 then arrives with a larger value, every exponential we computed for chunk 1 was measured against the wrong m. Its contribution to l and O is now stale.

Question

Can we repair chunk 1's stale partial sums without re-reading chunk 1? What single scalar relates "exponentials against the old max" to "exponentials against the new max"?

Act 1 · The Mathematical Key

The Derivation: Streaming Online Softmax

The key insight: as new chunks stream in, update to the latest max first. The new chunk needs zero rescaling. Only the past accumulator is scaled down by a single factor α.

The Streaming Update Algorithm

Suppose we have running state from past tokens: max mprev, sum lprev, and unnormalized output Oprev.
Now, a new chunk of keys arrives with raw dot products Sj.

1. Update to Latest Global Max First:
   mnew = max(mprev, maxj Sj)

2. Scale factor for PAST state only:
   α = e(mprev - mnew)

3. Rescale past accumulator & add new chunk directly:
   lnew = (lprev · α) + Σj e(Sj - mnew)

4. Rescale past output & accumulate new values:
   Onew = (Oprev · α) + Σj (e(Sj - mnew) · Vj)
Observation

The update is asymmetric. Because we compute mnew before touching the new chunk, its exponentials are already measured against the right max. Only the past state gets multiplied by α. Keep this in mind: if we ever compute two chunks independently and merge them afterwards, both sides will need rescaling. That case is coming.

Question

This looks right algebraically. Does it actually reproduce the exact softmax probabilities when we run it on real numbers?

Core Takeaway

We never store the attention scores matrix. We compute dot products, update m and l, accumulate into O, and discard S from registers immediately!

Why this matters for CUDA:

Notice that at no point did the algorithm allocate an array of size 4. It only ever maintained three scalar variables: m (current max), l (current denominator), and the vector O. In a GPU, these live entirely inside a thread's private register file (~1 cycle access).

Observation

The math is exact and the working set is three registers. We're ready to write a kernel. But full prefill means tiling an 8,192 × 8,192 problem across both Q and K at once.

Question

Is there a simpler case where we can validate Online Softmax on real silicon first, one where Q is a single row and only K needs to stream?

Act 2 · Starting Small

First Target: The Decode Phase

Decode is the simpler case: Q is a single token, so only K and V need to stream. We implement Online Softmax here first. The initial benchmark is not what we hoped for.

The Initial Benchmark

We map 1 thread block to each attention head: Grid: (32 heads, 1 batch). Each block streams through all 8,192 keys using the Online Softmax update we just derived.

Implementation Per Token Total (32 tok) Status
PyTorch Native (BF16 Baseline) 0.61 ms 19.4 ms 1.00x (Baseline)
Our CUDA Implementation 1.50 ms 48.1 ms 0.40x (2.5x SLOWER!)
The Hardware Trap: SM Starvation
An NVIDIA L4 has 58 SMs. Launching only 32 blocks leaves 26 SMs (45% of the GPU) idle, and each active block must walk all 8,192 keys one after another. Nearly half the chip never does any work.
Observation

We fused every operation and never wrote an intermediate to VRAM, yet we're 2.5x slower. Look at the launch: batch = 1 × 32 heads is only 32 blocks for 58 SMs. And look at the signature: the kernel wants FP32 with one K/V head per query head, so every step first has to convert the model's BF16 cache and expand 8 KV heads to 32 before the kernel can even start.

Question

Take the parallelism problem first. In prefill we'd split across query rows. But in decode Q is a single token. What other dimension of this problem can we split across the idle SMs?

Act 2 · Two-Stage Pipeline

The Solution: Split-K Decode Architecture

The answer is the sequence dimension itself. We split the 8,192 keys into 64 chunks of 128. Stage 1 distributes 2,048 blocks across the entire GPU; Stage 2 merges the partial results in thread registers.

Stage 1 · 2,048 Blocks (Saturate All SMs)

Grid: (64 chunks, 32 heads, 1 batch)

Each block loads 128 keys and 128 values. Computes local attention scores against the broadcasted Query.

// Block writes its partial summary to VRAM:
partial_m[block_idx] = local_m;
partial_l[block_idx] = local_l;
partial_O[block_idx * 64 + k] = local_O[k];

Now 2,048 blocks flood all 58 SMs (~35 blocks/SM), hiding global memory latency completely!

Stage 2 · 32 Blocks (Merge in Registers)

Grid: (32 heads, 1 batch) · 64 Threads

One block per head reads the 64 partial results and merges them directly in thread registers.

// 1. Pass 1: Global max across 64 chunks (64 cycles)
float global_m = -1e20f;
for (int i = 0; i < num_chunks; ++i)
    if (partial_m[i] > -1e19f) global_m = max(global_m, partial_m[i]);

// 2. Pass 2: Rescale and merge in thread registers
float global_l = 0.0f, global_O_k = 0.0f;
for (int i = 0; i < num_chunks; ++i) {
    if (partial_m[i] > -1e19f) {
        float exp_diff = expf(partial_m[i] - global_m);
        global_l += partial_l[i] * exp_diff;
        global_O_k += partial_O[i*64 + k] * exp_diff; // Coalesced!
    }
}
// 3. Final normalization:
O[k] = global_O_k / global_l;
Observation

Stage 2 is the symmetric merge we flagged on Slide 5: the 64 partials are independent, so every one must be rescaled to a common max. Scanning global_m first costs 64 cycles and buys a lot: half the expf() calls of a streaming merge, no repeated accumulator rescaling, and fully coalesced reads from partial_O.

Question

With 2,048 blocks now covering all 58 SMs instead of 32, the kernel should be substantially faster than our first attempt. Does that show up end-to-end against PyTorch?

Question

What exactly happens between the model's BF16 cache and our kernel's float* argument on every step, and why would it cost as much as the kernel itself?

Act 2 · Reading the Call Site

The Reason: We're Paying a Conversion on Every Step

Look at how the kernel is called from the model, not at the kernel itself. The problem is in the two lines before the launch.

The Call Site 
# Inside every attention layer, every decode step:
k = k_cache[:, :, :n, :].to(torch.float32).contiguous()
v = v_cache[:, :, :n, :].to(torch.float32).contiguous()
out = splitk_decode(q.float(), k, v, n)   # our kernel

LLaMA-3.2-1B stores its KV cache in BFloat16. Our kernel's signature is const float*. The only way to connect them is to manufacture an FP32 copy, and the model has to do it again on the next token because the slice has grown by one.

What Those Two Lines Cost
K: 8 heads × 8,192 × 64 × 4 B = 16.8 MB written
V: 8 heads × 8,192 × 64 × 4 B = 16.8 MB written
Per layer, per token: 16.8 MB read, 33.5 MB allocated + written
× 16 layers = ~0.5 GB of traffic per generated token

Two fresh allocations whose shape changes every step, two extra kernel launches, and twice as many bytes written as the cache actually holds, all before the attention kernel is even queued. None of it is attention. It exists only to satisfy a type signature.

Observation

The kernel reads 4-byte values that were 2-byte values a moment ago. We are not converting because the math needs FP32 inputs in memory; we are converting because we wrote float* in the function signature.

Question

What if the kernel accepted the BFloat16 pointers exactly as they sit in VRAM and did the FP32 upcast inside registers, one value at a time? The arithmetic stays FP32; only the loads change. Does the conversion step disappear entirely?

Act 2 · Production Integration

The Fix: Take BFloat16 Directly

Change the signature, not the math. The kernel now accepts __nv_bfloat16* straight from the model's cache and upcasts each value to FP32 inside a register as it loads it.

1. On-The-Fly Upcast in Registers

Declare the kernel over __nv_bfloat16. Convert in one instruction as each value arrives:

// Load 16-bit key & hardware upcast to FP32:
__nv_bfloat16 k_raw = K_cache[offset];
float k_fp32 = __bfloat162float(k_raw);
dot += q_reg[k] * k_fp32; // FP32 register math
Zero conversions in Python. The two red lines from the previous slide are deleted. The model hands the kernel its cache exactly as it is stored, and the accumulation stays in FP32 so numerics are unchanged.

Deleting two lines of Python bought 0.15 ms per token. Now ask what the kernel is doing with the memory bus: it reads 16.8 MB of K/V in 0.46 ms, about 37 GB/s on a 300 GB/s bus. Decode is supposed to be memory-bound, and this kernel isn't close. With one thread per key, adjacent threads read addresses a full key row apart (128 B), so the loads are uncoalesced. That is the next 4–5x, and it belongs to a later chapter.

Question

Decode had one query row, so streaming K and V was enough. Prefill is 8,192 query rows against 8,192 keys, and we already know that score matrix cannot exist in VRAM. Where do we cut it, and does anything we've built so far carry over?

Act 3 · The Full FlashAttention

Scaling to Prefill: Two Cuts, Same Trick

In prefill, Q is the whole prompt: 8,192 rows against 8,192 keys. We already know we cannot write that score matrix to VRAM. So where do we cut it, and what do we already know that helps?

0 · The Full Matrix

Per head, S = Q Kᵀ is [8192 × 8192].

32 heads × 8192² × 4 B = 8 GiB
VRAM: no. SRAM: not even close.

Materializing it is exactly what crashed PyTorch on Slide 3.

1 · Cut Along Queries

Slide 2 said output row i depends only on Qi and all of K, V. So give each block a stripe of 128 query rows and the entire K, V.

Grid: (8192 / 128 = 64, 32 heads, 1)
= 2,048 independent blocks
Block: 128 threads, 1 thread = 1 query row

No dependency between stripes; trivially parallel. But each block still faces a [128 × 8192] slab: 4 MiB of scores, and one thread's row alone is 32 KB.

2 · Stream Along Keys

Too many columns is the problem we solved on Slide 5. Walk the keys in chunks of 128 and keep only running state per row.

Per thread, in registers:
  m, l, O[64], scores[128]
Per block, in shared memory:
  the current 128-key chunk of K and V

A thread never holds more than 128 scores at once. The 8,192-wide row is never materialized.

// One block = 128 query rows. One thread = one row.
float q_reg[64];  // my query row, loaded once
float o_reg[64] = {0};  float m = -INF, l = 0;

__shared__ float smem[128][64];  // 32 KB, holds K then V

for (int k_chunk = 0; k_chunk < 8192 / 128; ++k_chunk) {
    smem[tx][:] = K[k_chunk*128 + tx][:];   __syncthreads();
    // 128 dot products for my row -> scores[128], chunk max
    __syncthreads();  // everyone done with K
    smem[tx][:] = V[k_chunk*128 + tx][:];   __syncthreads();
    // Online Softmax update of m, l, o_reg (Slide 5)
}
O[my_row][:] = o_reg[:] / l;
Observation

Nothing new was invented. Cut 1 is the row-independence from Slide 2; cut 2 is the streaming update from Slide 5, run by 128 threads side by side. The one new ingredient is shared memory: all 128 threads need the same key chunk, so the block loads it once. K is dead by the time V is needed, so a single 32 KB buffer serves both and we stay under the 48 KB static limit.

Question

This loop lets every query row look at all 8,192 keys. But the model is autoregressive: token i may only attend to keys j ≤ i. Where does that check belong, and what does a branch inside the hot loop cost on a GPU?

Act 3 · Warp Divergence Optimization

Causal Masking & Warp Divergence

Autoregressive LLMs cannot look into the future: token i can only attend to tokens j ≤ i. How do we implement this without destroying GPU branch performance?

Zone 1 · Past Chunks (j < i)

All 128 keys are strictly in the past for all 128 queries. Zero branches needed! Branchless execution at maximum speed.

Zone 2 · Diagonal Chunk (j == i)

The only block where queries and keys overlap. Confine all causal masking branches strictly to this single block.

Zone 3 · Future Chunks (j > i)

All keys are in the future. Do not even load them into SRAM! The outer loop stops at k_chunk <= q_chunk.

Observation

A naive if (col > row) on every element would diverge every warp on every chunk. But the mask only has structure at one place: the diagonal. Chunks strictly in the past need no check at all, and chunks strictly in the future are never loaded. Pruning the future halves total compute (N² / 2) and confines all divergence to 1 chunk out of every 64.

Question

The prefill kernel now compiles, fits in 32 KB of SRAM, and handles causality cleanly. How does it compare to PyTorch's cuBLAS path, and does the answer change as the context grows?

The attention code our model actually runs dies at 8k. Even the leanest formulation PyTorch allows dies at 12k. Our kernel's extra VRAM is the output tensor and nothing else; it scales linearly in time and flat in memory.

The Hardware Trade-off: Tensor Cores vs. CUDA Cores

Why PyTorch leads at ≤ 8k: its matmuls run on 4th-gen Tensor Cores (~121 TFLOPs dense BF16 on the L4). Our kernel runs scalar FMA loops on CUDA cores (~30 TFLOPs FP32), roughly 4x less raw compute.

The O(N²) memory cliff: every PyTorch formulation allocates at least one full N × N × 32 tensor. At 16k that is 16 GiB even in BF16, before a single weight is loaded. FlashAttention never allocates it.

Observation

At 8k the lean PyTorch path is ~1.75x faster, but not because our algorithm is wrong: it has Tensor Cores and we have scalar FMAs. Past 8k the comparison stops mattering. PyTorch cannot run at all, while our kernel needs 0 GB of intermediate VRAM and keeps scaling.

Question

Step back. Prefill wanted SRAM tiling and data reuse. Decode wanted registers and Split-K. Same attention formula, opposite kernel designs. Why?

Act 4 · Architectural Synthesis

The Bifurcation of LLM Inference

Why real engines (vLLM, TensorRT-LLM) use completely different kernels for Prefill vs Decode.

Prefill Phase · FlashAttention

Compute-Bound (High Arithmetic Intensity)

Arithmetic intensity is ≈ (128 × 128) / (128 + 128) = 64 FLOPs/byte.

  • SRAM data reuse is king.
  • Tens of thousands of multiply-accumulate operations per load.
  • Goal: Keep Tensor Cores and FP32 units 100% saturated.
Decode Phase · FlashInfer / PagedAttn

Memory-Bound (Low Arithmetic Intensity)

Arithmetic intensity is ≈ (1 × 128) / (1 + 128) ≈ 1 FLOP/byte.

  • VRAM memory bus saturation is king.
  • Almost no arithmetic reuse; keys are read once and discarded.
  • Goal: Bypass SRAM, use registers, maximize 128-bit memory bus bandwidth.
The Rule of Thumb: Never use a Prefill kernel for Decode, and never use a Decode kernel for Prefill. They stress opposite sides of the silicon.

Epilogue · Engineering Rules

The 5 Cardinal Rules of GPU LLM Inference

What the metal taught us.

  1. O(N²) Memory is a Choice, Not a Law of Physics: Intermediate attention matrices do not need to exist in VRAM. Online Softmax allows calculating the exact output in O(1) memory.
  2. Read the Call Site, Not Just the Kernel: Two lines of Python that converted the BF16 cache to FP32 on every token cost as much as the Split-K speedup itself. Deleting them took decode from a tie with PyTorch to 1.3x faster. A kernel's signature is part of its performance.
  3. Temporal SRAM Reuse Beats Static Limits: If K and V don't fit in shared memory at once, load K, compute dot products, and overwrite the same buffer with V.
  4. Confine Warp Divergence to the Diagonal: In causal masking, every chunk except the diagonal is strictly past or strictly future. Past chunks run branchless; future chunks are never loaded.
  5. Check Your Roofline Before Claiming It: "Decode is memory-bound" is a statement about the problem, not about your kernel. Ours moves 16.8 MB in 0.46 ms, about 37 GB/s on a 300 GB/s bus, because one-thread-per-key loads are uncoalesced. The bus is mostly idle, and that gap is where the next speedup lives.
The fundamental lesson: memory movement, not arithmetic, dictates GPU performance. Every kernel in this chapter was derived by asking where the bytes live, not by counting FLOPs.
