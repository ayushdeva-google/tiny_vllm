Deriving Flash Attention

From First Principles to a 2.3x Speedup

A step-by-step reconstruction of how we broke the $O(N^2)$ memory wall.

1. The $N^2$ Memory Wall

In standard Attention, PyTorch computes:
Scores = Q × K^T

For an 8,192 token prompt and 32 heads, this creates an intermediate matrix that is
1 × 32 × 8192 × 8192 × 4 bytes = 8.5 GB.

This happens before the Softmax is even applied. The GPU physically cannot hold this in SRAM, forcing massive, slow read/writes to global VRAM. Eventually, PyTorch simply crashes with an OOM Error.

2. The Mathematical Key: Online Softmax

To fix this, we realized we must compute Softmax iteratively without seeing the whole array at once. But Softmax requires the maximum value (to avoid overflow) and the total sum of the denominator.

The Derivation:

If we have an old max $m_{prev}$ and a new chunk max $m_{curr}$, the new global max is $m_{new} = max(m_{prev}, m_{curr})$.

To keep the denominator correct without recalculating, we just scale the old denominator by the difference in maximums:

$l_{new} = l_{prev} \times e^{m_{prev} - m_{new}} + \sum e^{x_i - m_{new}}$

3. First Attempt: The Decode Phase

We started our CUDA journey with the Decode Phase, where $Q$ is just 1 token.

  • Memory is $O(N)$ here, not $O(N^2)$, making it easier to test our math.
  • We used a Split-K approach: breaking the $K, V$ sequence into chunks.
  • Each GPU block computed attention for one chunk of tokens independently, passing partial_O, partial_m, and partial_l to a Stage 2 kernel to combine.

But when we ran the profiler, it looked like we were SLOWER than PyTorch!

4. The Invisible Bottleneck: The "Cast Tax"

Our raw Split-K kernel was clocking 0.108 ms compared to FlashDecode's 0.211 ms.

Why did PyTorch report us taking 2.5 ms?

The Culprit: The model weights were native BFloat16. Our C++ kernel required Float32. The Python command tensor.to(torch.float32).contiguous() took a massive 2.17 ms to run, completely masking the kernel's 2x speedup under a layer of data-wrangling overhead!

5. Tackling the Beast: Prefill Phase

With Decode conceptually verified, we tackled Prefill ($Q$ > 1 token). Here, we chunked $Q$ into blocks of 128 tokens, meaning one thread block processed 128 queries against the entire sequence.

6. Causal Masking: A Subtlety

We derived a critical insight about causal masking (where query $i$ cannot see key $j$ if $j > i$):

  • We don't need to put if (col > row) checks inside every loop!
  • If the chunk of K is strictly before the chunk of Q ($j\_chunk < i\_chunk$), we skip the check entirely.
  • If the chunk of K is strictly after the chunk of Q ($j\_chunk > i\_chunk$), we don't even load it!
  • We only do branch-heavy masking on the diagonal chunk ($i\_chunk == j\_chunk$).

7. The Reality Check: Why was Decode slow?

We ran our unified code on 8192 tokens. Prefill worked beautifully, but Decode clocked in at a miserable 156 ms (vs PyTorch's 55 ms). What went wrong?

1. Sequential Math Bug

We put the 128 dot products inside an if (threadIdx.x == 0) block. One thread was doing 100% of the math sequentially while 127 threads sat perfectly idle!

2. SRAM Bottleneck

For Decode (1 Query), routing data through Shared Memory `smem_K` and `smem_V` was completely unnecessary overhead for the tiny math ratio.

8. The Warp-Optimized Fix

We rewrote the hardware mapping to treat the GPU like a vector-machine:

  1. 1 Thread = 1 Token. All 128 threads load $K$ for their specific token directly from Global Memory into Registers.
  2. They all compute the dot product with the broadcasted $Q$ simultaneously.
  3. We use a fast Tree Reduction in shared memory to find the block-wide maximum $m$ and sum $l$ in just $\log_2(128)$ steps.
  4. We load $V$ straight to registers, weight it, and use a perfectly coalesced shared-memory transpose to sum the outputs.
