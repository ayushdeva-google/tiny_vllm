🎯 Key Profiling Insights & Hardware Observations:
  • O(N²) Quadratic Attention Scaling: In the absence of a KV cache, token decode latency escalates steeply (~5× to 7×, from ~70 ms at early steps to ~450+ ms at 2048 tokens), with Attn_Compute ballooning from under 1 ms to ~350–400 ms (~80% of entire step latency).
  • Host Overhead Amortization: At short context lengths, individual GPU kernels complete in microseconds so the GPU sits starved for work waiting on CPU dispatch (duty cycle ~15–30%). At long context, the massive attention computation keeps the GPU saturated (~95–98% duty cycle), completely hiding host launch latency.
  • Grouped-Query Attention Asymmetry: Measured kernel execution times reflect the exact architectural 4:1:1 parameter ratio between Query (about 0.6–0.9 ms, ~8.39 MB weights) and Key/Value projections (~0.25 ms, ~2.10 MB weights each).
  • SwiGLU FFN Asymmetry: Gate+Up takes ~2× to 2.5× longer than Down (about 5–6 ms vs ~2–2.5 ms at early steps; ~35 ms vs ~18 ms at late steps) because it evaluates two independent GEMM matrix multiplications streaming 2× the weight volume (~67.11 MB vs ~33.55 MB per layer).

📖 Section E: Systems & Architecture Glossary
Clear definitions of physical hardware metrics, execution overheads, and architectural mechanisms profiled in this report.
⚡ Active GPU Duty Cycle (%)
The percentage of wall-clock token generation time that the GPU execution units (Streaming Multiprocessors / SMs) were actively running kernel instructions on silicon, calculated as (Total Measured Kernel Duration / Total Wall-Clock Time) * 100.

Key Insight: At early decode, duty cycle is relatively low because kernels finish in microseconds and the GPU waits on CPU dispatch. At longer sequence lengths, duty cycle climbs toward near-100% saturation as the GPU becomes fully occupied recomputing quadratic full-sequence attention without a KV cache.
⏱️ Host CPU Launch & Driver Gaps
The measured dead time where the GPU sits idle with an empty execution pipeline waiting for the host CPU Python thread to enqueue the next operation.

In PyTorch, Python overhead and CUDA driver launch latency typically take tens of microseconds per kernel. When individual micro-kernels (e.g. RMSNorm, RoPE) execute faster than the CPU can enqueue them, the GPU drains its queue and starves for work.
🔥 Active GPU Kernel Execution Time
The total duration that GPU Streaming Multiprocessors (SMs) were actively executing CUDA kernels on silicon for the forward pass, measured directly via CUDA driver timestamps and GPU hardware timers.

Together with Host CPU Launch Gaps, it physically partitions 100% of measured wall-clock step latency into active GPU execution vs. host dispatch waiting.
🚀 Autoregressive Decode vs. Prompt Prefill
Prefill (Step 0): All prompt tokens are processed simultaneously in parallel via large Matrix-Matrix multiplies (GEMM, M = seqlen). This yields high arithmetic intensity on GPU compute cores.

Decode (Subsequent Generation Steps): Tokens are generated sequentially one by one. In our un-cached baseline, each new token step reruns the entire sequence history through all layers.
📦 Key-Value (KV) Cache & Quadratic Penalty
In standard LLM serving (e.g. vLLM), past Key and Value activation vectors are cached in GPU memory so each decode step only computes Q for 1 token and attends to cached K and V.

Without KV cache (our current baseline): The model discards past activations, forcing full recomputation of all past tokens at every step—causing attention computation to scale as O(N²) and linear layers as O(N).
🔬 Section F: Expected Results & Systems Invariants
Empirical validation checklist verifying theoretical LLM systems invariants against measured execution data.
📌 Note on Architectural Specs & Latencies: Parameter counts, dimensions, and weight footprints (MB) below are exact physical specifications of LLaMA-3.2-1B. Quoted millisecond latencies are typical benchmark approximations (observed on NVIDIA L4 GPUs) and may vary slightly across runs, prompts, and host CPU system load.
🔬 Invariant 1: GQA 4:1:1 Projection Asymmetry (W_q vs. W_k & W_v)
LLaMA-3.2-1B utilizes Grouped-Query Attention (GQA: Ainslie et al., 2023) with 32 Query heads and 8 Key/Value heads (head dimension 64 across 16 layers).
  • W_q Projection: 2048 ➔ 32×64 = 2048 (~8.39 MB weights, 4.19M params per layer)
  • W_k Projection: 2048 ➔ 8×64 = 512 (~2.10 MB weights, 1.05M params, 4:1 GQA ratio)
  • W_v Projection: 2048 ➔ 8×64 = 512 (~2.10 MB weights, 1.05M params, 4:1 GQA ratio)
Empirical Invariant: In measured breakdowns, Q_Linear takes about 0.6–0.9 ms per step, while K_Linear (~0.25 ms) and V_Linear (~0.25 ms) are virtually identical to each other and about 3.5× to 4× smaller, directly matching their physical parameter volume under GQA!
📈 Invariant 2: Quadratic O(N²) Attention Scaling Without KV Cache
Because past keys and values are not cached in memory, each layer recalculates the entire causal attention score matrix Q * K^T, triangular mask, softmax, and P * V across the full sequence history from token 0 to token N.
  • Step #0 (Prefill): Attention compute takes about 0.5–1 ms (~1% of step latency).
  • At ~1000 tokens: Attention compute escalates to about 100 ms (~60–65% of step latency).
  • At 2000+ tokens: Attention compute explodes to about 350–400 ms (dominating ~75–80% of step latency).
This steep exponential growth is the mathematical and empirical proof of why KV caching is mandatory for LLM inference engines.
⚖️ Invariant 3: SwiGLU FFN Asymmetry (Gate+Up vs. Down)
LLaMA-3.2 employs the SwiGLU Feed-Forward Network (Shazeer, 2020) with hidden dimension 2048 and intermediate dimension 8192 across 16 layers:
FFN(x) = (SiLU(x * W_gate) ⊙ (x * W_up)) * W_down
  • Gate + Up Projections (2× Weights & FLOPs): Evaluates two separate matrix multiplications (W_gate and W_up), streaming ~67.11 MB weights per layer (~1.07 GB across 16 layers).
  • Down Projection (1× Weights & FLOPs): Evaluates a single matrix multiplication (W_down), streaming ~33.55 MB weights per layer (~537 MB total).
  • Why Early Steps Stretch to ~2.5×: In unfused execution, separate kernel launches for gate_proj and up_proj double launch overhead and write two wide 8192-dim intermediate activation tensors to VRAM before Down compresses them back to 2048.
Empirical Invariant: Across all checkpoints, Gate+Up consistently takes approximately 2× to 2.5× longer than Down (e.g. about 5–6 ms vs ~2–2.5 ms at early steps; about 35 ms vs ~18 ms at late steps), asymptotically stabilizing near the theoretical 2:1 parameter ratio as context expands into compute saturation.
🎯 Invariant 4: Constant O(1) Flatness of LM_Head
While attention expands quadratically and linear projections grow with context length, the vocabulary projection (LM_Head) remains strictly flat:
logits = self.lm_head(h[:, [-1], :]) # Only projects the final token slice!
Because it multiplies only the single final token hidden state [1, 1, 2048] × [2048, 128256], it streams the exact same ~525.3 MB vocabulary weights at every step. Its measured latency stays virtually constant at about 2 ms from Step 0 to Step 2048!
🔄 Invariant 5: Duty Cycle Inversion (Host-Bound ➔ Attention-Saturated)
At early steps (0–250), GPU execution finishes in about 15–20 ms while host CPU dispatch overhead takes about 40–80 ms, keeping the GPU idle most of the time (Duty Cycle ~15–30%).

As sequence length grows, the quadratic attention computation swells GPU execution time to hundreds of milliseconds. Because GPU kernel execution duration increasingly dwarfs host dispatch latency, CPU overhead is hidden in the background, driving GPU duty cycle to about 95–98% saturation.
